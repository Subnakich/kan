# Kan: первый запуск на kanban.trisoft.ru

Новая версия заменяет экспорт через gateway на polling-очередь. Для нее достаточно существующего service token и IP whitelist; gateway URL/token не используются. Контракт: [bot-redmine-polling-contract.md](../docs/bot-redmine-polling-contract.md). Завершение обновления рабочего сервера до этой версии не подтверждено: необходимы аддитивная миграция `AddRedminePollingQueue` и совместимый worker бота. Исторические install/upgrade скрипты ниже не являются установщиком этой версии.

## Обновление плоской установки: polling-4

`deploy/polling-upgrade-root.sh` запускается из проверенного пакета под root. Рабочие пути остаются `/opt/kanban/compose.yml` и `/opt/kanban/.env`; новые каталоги releases не создаются. Бот не обновляется этим скриптом.

- Проверяет старый образ, Compose/volume/loopback, предыдущую миграцию, закрытый API, HTTPS, Redmine и доступные ресурсы.
- Сохраняет `.env` побайтово. Меняет образы web/migrate и убирает неиспользуемые gateway URL/token из окружения web. По умолчанию расхождения рабочих ключей/whitelist запрещены; явный режим применения описан ниже. В плоском Compose теги образов записаны явно; прежняя переменная `KAN_RELEASE` не определяет активный образ.
- Собирает amd64 с лимитом builder 3 GiB / 2 CPU, пока приложение работает; выполняет аудит образа до остановки.
- Короткая пауза только Kan: dump, восстановление в отдельную временную БД, сверка fingerprints, аддитивная миграция очереди, проверка неизменности всех прежних таблиц и функций, запуск web.
- Проверяет закрытую регистрацию, доступность HTTPS/login/Redmine, прежний отказ API без авторизации и сохранность остальных контейнеров.
- Копия БД, предыдущий Compose, настройки и исходники находятся в root-only `/opt/kanban/backups/upgrade-20261006-task-control-4-polling`.
- До открытия сервиса ошибка вызывает откат БД/Compose/образа; после открытия восстановление старого dump автоматически запрещено. Не удаляет старые образы, данные и резервные копии.

Если пользователь изменил настройки интеграции в `.env`, но контейнер еще работает со старыми значениями, обычный запуск останавливается. Явный флаг `--apply-saved-integration` разрешает применить только `TASK_CONTROL_SERVICE_TOKEN`, `TASK_CONTROL_ALLOWED_IPS` и `TASK_CONTROL_TRUSTED_PROXIES`. Whitelist допускает только IP бота `46.203.233.110` (либо `/32`), trusted proxy — только фактический Docker gateway контейнера (либо `/32`), service token — не короче 32 печатных символов без пробелов. Любые расхождения DB/auth/прочих параметров запрещены. Gateway URL/token удаляются из нового окружения независимо от флага; `.env` не редактируется. Откат возвращает фактическое прежнее окружение web, а не новые значения из `.env`.

Для конкретного сбоя на сравнении окружения есть `--retry-preflight`: проверяет, что сборка/миграция/maintenance не начинались и исходные `.env`, Compose, runtime не изменились; затем переносит прежнюю подготовку в отдельный `backups/polling-preflight-*/attempt`, ничего не удаляя. После начатой сборки или миграции автоматическое продолжение запрещено. Явное применение и повтор подготовки можно совместить в одной команде.

Проверки подготовки: `bash -n deploy/polling-upgrade-root.sh`, `python3 tools/security/polling-layout.test.py`, `bash tools/security/polling-backup.test.sh`. Установка подтверждена только после строки `Kan upgraded to 20261006-task-control-4-polling` и внешней проверки. До этого статус — подготовлено, не задеплоено.

## Постоянная структура эксплуатации

`flatten-root.sh` переносит конфигурацию активного релиза в `/opt/kanban/compose.yml` и `/opt/kanban/.env`. Выполняется под root на сервере Kan с соседним `flat-layout.py`. Активный релиз определяется по Docker label, а не по наличию каталога.

- Копирует `.env` побайтово (права 600), сохраняет исходные файлы в отдельном root-only каталоге `backups/flat-layout-*`.
- Новый `compose.yml` записан в JSON-синтаксисе, допустимом в YAML/Compose. Сохраняет параметры и переменные, убирает только `build`: рабочий запуск использует готовые образы с тегами.
- Проверяет равенство раскрытых конфигураций и соответствие сохраненных настроек работающему web. При несоответствии останавливается, не применяя новые ключи неявно.
- Пересоздает только `web`, без зависимостей, сборки, скачивания образов или миграций. Существующие PostgreSQL, volume, аккаунты, Nginx и Redmine не меняются.
- Проверяет прежний image ID, health/login/политику API и неизменность остальных контейнеров. При сбое возвращает web на исходную конфигурацию без восстановления БД.
- Старые каталоги и образы не удаляет. После успешной проверки рабочие настройки редактировать только в `/opt/kanban/.env`. Старые скрипты install/upgrade, рассчитанные на конфигурацию в releases, больше не запускать.

Рабочий запуск после успешного переноса:

```bash
cd /opt/kanban
docker compose --env-file .env -f compose.yml up -d --no-deps --no-build --pull never web
```

Это команда для запуска/применения настроек, не для обновления версии. Следующее обновление требует отдельной проверки образа и миграций с резервной копией. `down -v` запрещен. Перенос не подтвержден до строки `Kan now uses ...` и внешней проверки.

Отдельный Compose-проект `trisoft-kan`, PostgreSQL 15, собственный volume. Redmine, его PostgreSQL 11, volumes и vhost не изменяются. На проверенном сервере Ubuntu amd64 работают Nginx и Certbot; Caddy нет. Порт 3100 свободен, DNS A указывает на сервер.

## Установка

Передать пакет текущих исходников с `RELEASE.sha256`: обычный clone GitHub пока не содержит локальных изменений. Не передавать `.env`, demo-БД, node_modules и тестовые compose-файлы. Пакет готовит `tools/security/package-release.mjs`.

В root-консоли запустить `bash /home/trs_redmine/kanban-release-20261006-task-control-2/deploy/install-root.sh`. Имя, email и пароль первого пользователя вводятся в терминале, пароль не сохраняется в аргументах/логах и не передается в чат.

Установщик:

1. Проверяет checksums, архитектуру, ресурсы, свободный порт, Nginx и доступность Redmine. Отказывается перезаписывать существующий релиз/vhost.
2. Копирует релиз в `/opt/kanban/releases/20261006-task-control-2`, сохраняет конфигурацию Nginx в `/opt/kanban/backups/first-install-20261006-task-control-2`, генерирует отдельные секреты в `deploy/.env` (600).
3. Если Buildx отсутствует, устанавливает только `docker-buildx`; предварительная apt simulation должна показывать 0 обновлений / 1 новый пакет / 0 удалений. Docker Engine/ОС не обновляет.
4. Собирает через отдельный Buildx builder с лимитом 3 GiB RAM, без swap, 2 CPU; после сборки останавливает builder, сохраняя его cache. Проверяет web-образ через npm advisory registry и прекращает запуск при High/Critical или недоступности registry.
5. Публикует только ACME HTTP endpoint; остальные запросы получают 503. Выпускает сертификат через существующий аккаунт Certbot, без неявного принятия новых условий.
6. Запускает собственную БД и миграции Kan. Создает первый аккаунт через loopback, закрывает регистрацию и проверяет фактический отказ.
7. Включает отдельный HTTPS vhost, оставляет API бота закрытым, проверяет health/API/Redmine, добавляет hook продления только для нового сертификата.

Сборка ограничена ресурсами, но полная изоляция от нагрузки диска/сети не гарантируется. Если установка прекращена, повторно не запускать вслепую: проверить указанные каталог и логи.

## После запуска

### Продолжение после сбоя HTTPS readiness

В первом запуске проверка HTTPS сразу после `nginx reload` получила прежний сертификат и выполнила откат. Сертификат Kan на диске корректен; два reload в одну секунду согласуются с гонкой применения конфигурации. В установщике добавлено ограниченное ожидание корректного HTTPS без отключения TLS verification. Bash/ShellCheck и четыре сценария регрессионного теста readiness прошли; root recovery еще не запускался.

Для существующего релиза использовать отдельный проверенный recovery-пакет `kanban-recovery-20261006-1`, скрипт `resume-root.sh`. Он проверяет оригинальные checksums, сертификат, закрытую регистрацию и существующий volume/account; только запускает прежние контейнеры, включает прежний vhost, ожидает HTTPS и добавляет renewal hook. Не пересобирает образы, не выполняет миграции, не меняет `.env`, не создает аккаунт. При ошибке снова отключает только свою новую ссылку vhost и останавливает Kan; данные остаются. Первоначальный `install-root.sh` повторно не запускать.

- Проверить HTTPS, вход, создание/перемещение/редактирование карточки и сохранение после рестарта. Убедиться, что 3100 и 5432 не доступны извне.
- Для бота заполнить service token, точный внешний IP в `TASK_CONTROL_ALLOWED_IPS` и `allow <IP>;` перед `deny all;` в `/etc/nginx/snippets/kanban-bot-allow.conf`.
- `TASK_CONTROL_TRUSTED_PROXIES` — точный TCP-адрес host Nginx, видимый из контейнера, не вся Docker-подсеть. Определить после запуска. Nginx перезаписывает X-Forwarded-For адресом клиента.
- Подключить настоящий bot gateway отдельно. Пока нет реальных уведомлений/выгрузки в Redmine; mock на production не используется. SMTP/S3 не настроены: почта и загрузка вложений не входят в первый запуск.

## Откат

Отключить только новый vhost `kanban.trisoft.ru`, проверить `nginx -t`, выполнить reload. Остановить только проект `trisoft-kan` через compose `stop`. Не выполнять `down -v`, не удалять данные/backup и не трогать `redmine-legacy`. Автоматическая обработка ошибки установщика отключает только свою новую ссылку vhost и останавливает Kan; файлы, БД и cache сохраняются. Перед будущими обновлениями Kan требуется проверенный backup/restore его собственной БД.

## Обновление интерфейса и ответственного: task-control-2 → task-control-3

Первый запуск/recovery уже завершен: Kan работает через HTTPS, регистрация и интеграционный API закрыты. Исторические проверки первого запуска выше не описывают текущий статус сервера.

`upgrade-root.sh` — отдельный скрипт только для перехода с `20261006-task-control-2` на `20261006-task-control-3`. Не запускать повторно `install-root.sh`.

1. Проверяет текущий образ, исходный Compose, собственный volume Kan, checksums, HTTPS, закрытые signup/API, конфигурацию Nginx и доступность Redmine.
2. Копирует существующий `.env`, заменяя только метку релиза. Секреты, аккаунты, настройки API сохраняются.
3. Собирает amd64 web/migrate с лимитом builder 3 GiB / 2 CPU. Пока Kan продолжает работать. Аудит npm metadata блокирует High/Critical до остановки приложения.
4. Временно возвращает 503 только на vhost Kan, останавливает только его web. Создает custom-format dump в `/opt/kanban/backups/upgrade-20261006-task-control-3/kan.dump`.
5. Восстанавливает dump в отдельную временную БД того же Kan PostgreSQL. Проверяет все таблицы, журнал миграций и определения task-control функций по fingerprints, удаляет только временную проверочную БД.
6. Выполняет миграцию, проверяет сохранность аккаунтов/задач/описаний/сроков/таймеров, прежних основных ответственных и участников. Запускает новый web, проверяет health и реальный отказ регистрации.
7. Возвращает исходный Nginx-файл, проверяет внешний HTTPS/login, API=403 и Redmine. Старый релиз, образы и проверенная копия БД остаются.

При ошибке до открытия сервиса скрипт автоматически восстанавливает собственную БД Kan (если миграция началась) и старый web. После открытия автоматический откат БД запрещен: он мог бы удалить новые действия пользователей. При таком сбое нужно диагностировать новый сервис/прокси, не восстанавливать старый dump вслепую.

Проверено локально: Bash syntax/ShellCheck, реальный PostgreSQL dump/restore и откат старого guard, fingerprints данных и журнала миграций. Полный root-скрипт на сервере требует отдельного запуска; его завершение подтверждается строкой `Kan upgraded to ...` и повторной внешней проверкой.

```bash
node tools/security/package-release.mjs 20261006-task-control-3
bash tools/security/upgrade-backup.test.sh
```
