# Kan: контроль поручений

Текущий экспорт работает через **polling-очередь, только бот → Kan**. Новый контракт и endpoints: [bot-redmine-polling-contract.md](bot-redmine-polling-contract.md). Старые сведения о входящем gateway ниже сохранены как исторические; URL/token gateway новой версии Kan не нужны. Завершение обновления production до polling-версии пока не подтверждено.

Форк: https://github.com/Subnakich/kan. Ветка: `feat/trisoft-task-control`.
База разработки: `d0809f0`. Код бота ведется отдельно в `/Users/subnak/dev/redmine-bot`; эта документация описывает изменения Kan, не подтверждает развертывание бота.

## Локальный запуск

Требуется Docker с Compose. Порт 3100 должен быть свободен.

```sh
docker compose -f compose.local.yml up -d --build
docker compose -f compose.local.yml exec -T web node tools/task-control/seed-local.mjs
```

Открыть http://localhost:3100. Демонстрационный аккаунт: `alan@kan.local`, пароль `Kan-local-demo-2026!`. Эти учетные данные и токены из compose предназначены только для локального стенда.

Первый запуск устанавливает зависимости и применяет миграции. Приложение слушает только `127.0.0.1:3100`; PostgreSQL и mock-шлюз не публикуют порты. Отдельный проект `trisoft-kan-local` и отдельные volumes; существующие контейнеры не затрагиваются.

```sh
docker compose -f compose.local.yml logs --tail=100 web
docker compose -f compose.local.yml stop
docker compose -f compose.local.yml up -d
```

Остановка сохраняет данные. Не использовать `down -v`, если данные нужны.

## Реализовано

- Opt-in режим Task control на пустой доске. Создает или использует колонки Review, Queue, In Progress, Blocked, Done. Роль колонки хранится независимо от названия: переименование и перестановка не меняют логику.
- Точный срок до минуты: ввод и отображение в Europe/Moscow, момент в UTC в интеграционном API. Просрочка сравнивается с текущим временем; Done не подсвечивается как просроченная.
- Один основной ответственный — из штатных участников карточки. Единственный участник назначается автоматически; при нескольких можно выбрать основного среди них. Импорт назначенного ответственного также добавляет его в Members. Изменения участников обновляют снимок для бота.
- Review допускает неизвестный срок и ответственного. Подтверждение только через Queue; требуются непустые название/описание и ответственный. Срок необязателен во всех колонках. Blocked требует причину. Проверки действуют и при прямых вызовах штатного API.
- Импорт одной задачи через сервисный API: источник/цитата, критерии, настоящий чеклист и метки. Неизвестный owner сбрасывается и отмечается для уточнения на Review.
- Устойчивый импортный ключ, SHA-256 содержимого, атомарный конкурентный импорт. Повтор возвращает ту же карточку; измененное содержимое — 409; удаленная задача — 410.
- Revision, deadline_revision, column_entered_at, column_visit_id. Комментарий/сортировка не сбрасывают пребывание в колонке. Изменения комментариев, чеклистов, вложений и связей меток тоже повышают revision.
- Транзакционный журнал изменений PostgreSQL с cursor и пагинацией. Бот может восстановить чтение после отключения. События содержат технические идентификаторы, а не копии транскрибации.
- Удаление отдельной карточки Task control физически удаляет ее запись и дочерние записи; импортный ключ остается как tombstone. Обычные доски сохраняют штатный soft delete. Удаление Kan-карточки не удаляет Redmine issue.
- Интерфейс выбора проекта/справочников Redmine, preview полного снимка, подтверждение, проверка операции после ошибки. Actor определяется сервером из сессии. PostgreSQL хранит запросы; бот забирает их через service API. Kan не вызывает сервер бота, токены не отдаются браузеру.
- Ссылка Redmine, отметка устаревшего снимка после изменения карточки. Выгрузка не перемещает карточку и не прекращает контроль в Kan.

## Что сейчас демонстрационное / ограничения

- `tools/task-control/mock-gateway.mjs` — локальная заглушка, не Telegram-бот и не настоящий Redmine. Она хранит журнал в отдельном volume, проверяет revision/actor и повторные операции. `redmine.example.test` не является настоящим сервером.
- Реальная отправка уведомлений, график пн–пт 10–19, Telegram ↔ Kan ↔ Redmine mapping, перенос файлов и создание issues реализуются в `/Users/subnak/dev/redmine-bot` отдельным этапом. Без этого уведомления не отправляются.
- Вложения используют штатное S3-хранилище Kan. Локальный compose пока не настраивает S3; выдача файлов и удаление объектов из bucket требуют отдельной проверки/политики хранения. Записи вложений удаляются вместе с карточкой, но этот MVP не добавляет сборщик оставшихся S3-объектов.
- Перенос контрольной карточки между досками отклоняется. Миграция существующей непустой доски не выполняется автоматически. Нужно отдельно согласовать перенос/проверку старых задач.
- Критерии исходной задачи доступны в API; полноценное редактирование критериев и настройка порогов зависания в UI — следующий небольшой этап.
- Cursor списка карточек — обход по идентификаторам, не замороженный снимок. Бот сначала сохраняет cursor изменений, затем обходит карточки и дочитывает журнал; повторные события применяет идемпотентно.

## Сервисный API для бота

Префикс `/api/integrations/v1`. Заголовок `Authorization: Bearer <TASK_CONTROL_SERVICE_TOKEN>`. Не использовать этот токен как пользовательский API key Kan.

| Метод | Путь                                           | Назначение                                         |
| ----- | ---------------------------------------------- | -------------------------------------------------- |
| GET   | `/capabilities`                                | Instance ID, версия и функции                      |
| GET   | `/boards`                                      | Включенные активные доски и роли колонок           |
| GET   | `/boards/{board_id}/members`                   | Активные участники, public ID и имя                |
| GET   | `/boards/{board_id}/cards?cursor=...`          | До 100 снимков; `next_cursor`, `has_more`          |
| GET   | `/changes?cursor=...`                          | До 100 событий; `next_cursor`, `has_more`          |
| GET   | `/cards/{card_id}`                             | Текущий снимок карточки                            |
| GET   | `/cards/{card_id}/attachments/{attachment_id}` | Авторизованный redirect на S3 URL сроком 60 секунд |
| POST  | `/imports/cards`                               | Импорт ровно одной задачи в Review                 |
| GET   | `/imports/cards?external_key=...`              | Результат импорта / tombstone                      |
| PUT   | `/cards/{card_id}/redmine-link`                | Идемпотентная фиксация созданного issue            |

Все ID в контракте — public ID, не внутренние номера таблиц. API не раскрывает email участников. Сервис получает доступ только к доскам, на которых администратор включил Task control.

Импорт: `{external_key, payload_hash, board_id, meeting, task}`. Полная Zod-схема: `packages/api/src/routers/task-control.ts`. Пример payload: функция `importPayload` в `tools/task-control/client.mjs`.

- `external_key = instance_id:meeting.id:task.id`; сохранять независимо от содержимого и выбранной доски.
- `Idempotency-Key` должен совпадать с `external_key`.
- `payload_hash = sha256(canonical({board_id, meeting, task}))`; UTF-8, ключи объектов рекурсивно сортируются, порядок массивов сохраняется. Не менять payload между retry.
- У даты обязателен timezone (`2026-10-07T15:30:00+03:00` или `...Z`), неизвестный срок — `null`, не полночь.
- Ответ: `{card_id, board_id, status, payload_hash, created}`; 201 при создании, 200 при повторе.
- Журнал: `{items:[{event_id,card_id,revision,occurred_at,kind}], next_cursor, has_more}`. `kind`: created/updated/deleted/archived. Читать текущий снимок; 404/410 прекращают контроль. `column_visit_id` отличает новое посещение той же колонки. Исторического содержимого карточки в журнале нет.
- 401 — токен; 409 — конфликт ключа/связи; 410 — удаленный ключ/архив; 422 — неверный формат; 500/503 — временный сбой, повтор с тем же ключом. Не логировать исходные payload/токены.

## IP whitelist сервисного API Kan

Настройки серверные, через `.env`/Docker environment, не через пользовательский UI:

```dotenv
# Пример, заменить на реальный фиксированный внешний IP сервера бота:
TASK_CONTROL_ALLOWED_IPS=203.0.113.10
# Пример адреса reverse proxy, который непосредственно соединяется с Kan:
TASK_CONTROL_TRUSTED_PROXIES=172.20.0.2
```

- Разрешены отдельные IPv4/IPv6 и CIDR, несколько записей через запятую. IPv4-mapped IPv6 поддерживается.
- Whitelist применяется только к `/api/integrations/v1/*`; интерфейс и штатный API Kan не ограничиваются этим параметром. Токен обязателен и после проверки IP.
- Пустой `TASK_CONTROL_ALLOWED_IPS` отключает IP-фильтрацию для локальной разработки. Перед публикацией обязательно заполнить. Ошибочный IP/CIDR в любом из двух параметров закрывает API с 503; запрещенный источник получает 403.
- Без доверенного прокси учитывается только адрес TCP-соединения. `X-Forwarded-For`, `X-Real-IP`, `CF-Connecting-IP` от произвольного клиента не дают доступ.
- От доверенного TCP-пира разбирается только `X-Forwarded-For`: справа налево до первого недоверенного адреса. Прокси обязан перезаписать заголовок реальным клиентским IP либо дописать реальный адрес справа. Не доверять всему Docker/VPN диапазону без необходимости; лучше указать точные адреса контролируемых прокси. Не добавлять прокси в whitelist клиентов.
- Не открывать прямой порт приложения наружу. HTTPS, дополнительный whitelist и rate limit на reverse proxy остаются обязательной частью серверного развертывания. Новые настройки не являются аудитом безопасности всего Kan.
- После изменения Docker environment пересоздать только контейнер web (`docker compose up -d web` с нужным compose-файлом); не удалять volumes. На серверы этот этап ничего не устанавливает.
- При polling входящего gateway на сервере бота нет. Whitelist нужен на стороне Kan для исходящего IP сервера бота.

## Исторический контракт gateway (заменен polling)

Префикс `/internal/kan/v1`, bearer `TASK_CONTROL_GATEWAY_TOKEN`. Полный работающий пример ответов — mock gateway; Zod-ответы — `packages/api/src/utils/task-gateway.ts`.

- `GET /health` → `{api_version:"1.0", demo:false}`.
- `GET /redmine/projects?actor_member_id=...` → `{items:[{id,name}],has_more,next_cursor}`.
- `GET /redmine/projects/{id}/options?actor_member_id=...` → `{trackers,statuses,priorities,custom_fields}`. Справочники `{id,name}`; поле `{id,name,required,format,choices?}`.
- `POST /redmine/exports/preview` → `{preview_id,expires_at,snapshot,warnings:[],errors:[]}`. Вход `{actor_member_id,card_id,expected_revision,project_id,tracker_id,status_id,priority_id,custom_fields:[{id,value}]}`.
- `POST /redmine/exports` принимает `{actor_member_id,preview_id}` и постоянный ключ `kan:<instance_id>:<card_id>`. Preview привязан к actor, карточке, выбору и ревизии; проверять совпадение ключа с карточкой preview. Ответ `{operation_id,status,redmine_link,errors:[]}`.
- `GET /redmine/exports/{operation_id}?actor_member_id=...` — тот же формат. Статусы pending/created/linked/failed/unknown.
- `redmine_link`: `{instance_id,issue_id,display_id,url,exported_at,exported_revision}`. Callback PUT в Kan после создания. Повтор должен завершить linking, не создать второй issue.
- Ошибка `{code,message,retryable,operation_id}`. Неизвестный результат POST требует сверки с Redmine по внешнему маркеру, а не нового ключа.
- Реальный gateway обязан проверять права actor в Kan/Redmine, mapping ответственного и обязательные поля; переносить комментарии, чеклисты, критерии, метки, источник и файлы, точный срок включать в описание. Mock не доказывает эту интеграцию.

## Миграция / обновления форка

Добавлены только новые миграции. Старая схема не переписывается. Миграции проверяются также штатными тестами на свежих изолированных PGlite-базах; HTTP smoke работает с реальным PostgreSQL 15 локального стенда.

Перед переносом на сервер: отдельное окружение, резервная копия PG/S3, восстановление и тест, закрытые gateway/DB, новые секреты, HTTPS, проверка бота на тестовом проекте. Production не обновлять этим dev-compose.

Откат требует backup/restore либо совместимой версии схемы: у контрольных досок есть новые обязательные инварианты, поэтому запуск старого кода поверх новой базы не гарантируется. Для обновления upstream: отдельная ветка, merge/rebase, review миграций, регрессия/smoke, сборка релизного образа; лишь затем отдельное согласованное развертывание.

### Проверка участников и необязательного срока

```bash
docker compose -f compose.local.yml exec -T web node tools/task-control/ownership-test.mjs
docker compose -f compose.local.yml exec -T web node tools/task-control/ownership-migration-test.mjs
```

Первая проверка создает отдельное локальное рабочее пространство с тестовыми участниками. Вторая репетирует переход со старого правила в транзакции с ROLLBACK: сохранение основного ответственного и участников, назначение единственного участника, сохранность описаний и таймеров колонок.

Миграция `20261006142318_NativeTaskOwnership.sql` не требует срока и связывает основного ответственного со штатными участниками карточки. При переносе на сервер: backup базы Kan, остановка старого web, миграция, запуск нового web, проверка; Redmine не затрагивать. Старый web нельзя оставлять писать в новую схему: его импорт еще не создает штатных участников.
